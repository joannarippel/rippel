Exercise 3: Limiting Authentication Attempts

Install a security plugin to limit the number of failed login attempts on the WordPress site. Configure the settings to temporarily block IP addresses that attempt to brute-force the authentication portal.

I deployed the Wordfence security plugin to enforce rate limiting and temporarily block malicious IP addresses trying to force entry into the WordPress site.

Exercise 4: Implementing Multi-Factor Authentication

Configure multi-factor authentication (MFA) for your WordPress administrator account. Use a multi-factor authentication plugin or service to add an extra layer of security.

I used the Wordfence Login Security plugin to add a layer of Multi-Factor Authentication (MFA) to the administrator profile. The system generated a unique server-side QR code and a set of emergency recovery backup keys. I successfully verified the setup by entering the code and activating the policy, changing the account status to Active to block unauthorized access attempts.

With MFA status verified as active on the server, the site will now demand a physical token validation for every login session. This effectively completely neutralizes any online dictionary or brute-force simulation.

Exercise 5: Securing the HTTPS Connection

Install an SSL certificate and configure the WordPress site to use HTTPS connections. Ensure that all pages and forms are accessed over a secure connection.

I enabled HTTPS for my local WordPress site running in Docker by exposing port 443 and configuring Apache SSL inside the container. I enabled the SSL and rewrite modules in Apache and modified the .htaccess file to redirect all HTTP traffic to HTTPS. A self-signed TLS certificate was used because the site runs on localhost. Although Firefox shows a warning because the certificate is not issued by a trusted public Certificate Authority, the HTTPS connection is encrypted and working correctly.

I verified the HTTPS configuration by accessing the site through https://localhost and viewing the certificate information in Firefox Certificate Viewer.

I also tested the Really Simple Security plugin, but because the site runs on localhost with a self-signed certificate, automatic SSL detection and Let’s Encrypt configuration were not fully supported.

Security Hardening Measures Applied

Configuring Security Headers

To fix the missing HTTP security headers identified by Nikto, the .htaccess file was modified.
The following configuration was added:

<IfModule mod_headers.c>
Header always set X-Frame-Options "SAMEORIGIN"
Header always set X-Content-Type-Options "nosniff"
</IfModule>

a2enmod headers
service apache2 restart

These headers help protect the website against:

  • clickjacking attacks
  • MIME-type sniffing attacks

Blocking XML-RPC

To reduce the risk of brute-force attacks and abuse of the WordPress XML-RPC interface, access to xmlrpc.php was blocked.

<Files xmlrpc.php>
Order Deny,Allow
Deny from all
</Files>

Removing Exposed Information Files

rm /var/www/html/readme.html
rm /var/www/html/license.txt

After Hardening

Several hardening measures were implemented to improve the security of the application:

  • security headers were configured
  • XML-RPC access was blocked
  • exposed information files were removed

The final scan showed a significant improvement. Most of the previously identified findings were resolved.

Only one minor warning remained related to the X-Content-Type-Options header during the HTTP to HTTPS redirection process.

This warning is considered non-critical because the website redirects all traffic to HTTPS.

After remediation and re-testing, the final scans confirmed that no critical vulnerabilities were present and the overall security posture of the website was significantly improved.
